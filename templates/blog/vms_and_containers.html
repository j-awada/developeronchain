Virtualisation and Containerisation

June 20263 min read

Virtualisation

Hypervisor-based virtualisation enables running multiple operating systems in parallel by running them in virtual machines managed by a hypervisor. The hypervisor allocates hardware resources such as CPU, RAM and disk to each VM.

Hypervisors

Are software, firmware, or hardware platforms that create and run virtual machines. They can be split into 2 categories:

  • Type 1 (bare-metal) hypervisors: these run directly on the host's hardware to control the hardware and manage guest operating systems. Examples include VMware ESXi, Microsoft Hyper-V, and Xen.
  • Type 2 (hosted) hypervisors: these run on a conventional operating system just as other computer programs do. Examples include Oracle VirtualBox and VMware Workstation.

Containerisation

Containerisation or OS-level virtualisation is when the OS kernel supports multiple isolated user-space environments called containers. Containerisation engines include LXC.

Docker which is an application , uses its own containerisation engine libcontainer to create containers. The Open Container Initiative (OCI) was formed to standardise specs such as the container runtime. The Container Network Interface (CNI) provides specifications for container networking to make them less dependent on the hosting environment.

Docker architecture

The main entity of Docker is the Docker Engine which runs on top of the OS and consists of; among others, the Docker Daemon. The daemon use libcontainer to create the container environemnts.

In Docker, isolated container environments are implemented using Linux kernel featrues, for example:

  • Namespace: Docker creates Linux namespaces for process isolation, network and file system mounting. Process outside this namespace are not visible.
  • Control groups: Docker uses control groups to limit the resources each container uses.
  • Capabilities: this allows the container process to run using capabilities instead of running as superuser.

Container sandboxing

Used to increase the isolation of containers alongside the Linux kernel features mentioned above. This can be achieved by for example:

  • Placing a container on top of an OS running in a VM aka VM-based Sandboxing eg. Kata containers
  • Or by providing each container with its own kernel aka Container Kernel Sandboxing eg. gVisor

Kubernetes architecture

A set of worker nodes together with a master node form a cluster. The worker nodes run containers assigned by the master. The worker and the master nodes have different components:

Master node components
  • etcd: a key-value storage system to keep track of the state of the cluster
  • apiserver: is the main interface for interacting with the cluster. It is a REST API which accepts requests through HTTP. Each request is passed through authentication, authorisation and admission controllers to verify legitimacy.
  • scheduler: deploys or schedules pods onto nodes
Worker node components
  • kubelet: an agent which ensures containers are running inside pods according to the defined specifications of the pod
  • kube-proxy: it configures a proxy such that the pods can communicate with each other through proxy endpoints
  • container runtime: this is needed to run the containers on Kubernetes
Kubernetes networking

Kubernetes supports the CNI specification which assumes that all containers and nodes must be able to communicate with each other through IP without needing to perform IP translation beforehand i.e. without NAT. In reality, NetworkPolicy objects are used to control how pods communicate with each other via Labels. That is because pods are ephemeral with chaging IP addresses.
